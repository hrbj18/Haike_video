### 1.1 原始需求复述

现在这条「长直播素材进 → 短视频出」的链路已经能跑通，但有三处不满意：

1. **粗剪太慢**。视觉模型是**一个窗口一个窗口串着调**的（`backlot/material_interactions.py:553` 的 `for wi, window in enumerate(windows)`，每窗口一次付费调用，88.9 分钟 = **34 个窗口**）；腾讯 ASR 的分片也是**一片一片串着传**（`backlot/tencent_asr.py:541-549`，`CHUNK_SECONDS = 600`，88.9 分钟 ≈ **9 片**）。用户要的是「**粗剪主要针对速度**」。
2. **二次精剪的"基础剪辑"没做完**。渲染层目前**只有统一倍速 `atempo`**（`material_interaction_second_pass_render.py:186`），**没有音频淡入淡出**；停顿压缩每次都在语音边界硬切（实测一条成片 **13 处切口 = 26 个硬切点**），有**咔哒/爆音**风险；也**没有「等待段加速」这一原语**——现在等待段只能被整段删掉，导致跳切。
3. **两个开源项目的能力没复刻**。auto-editor 的看家本领之一是把**剪辑决策导出成剪辑软件能打开的工程**（`--export premiere|resolve|final-cut-pro|...`、OTIO），我们现在**完全没有导出**（`backlot/workbench.py` 内没有任何 export 接口），产物只有烧死的 MP4。用户的目标是「**帮助剪辑的小伙伴节省挑选素材的时间**」——只给成品，同事只能接受或重做；给出工程文件，我们的输出才从「结果」变成「起点」。

### 2.2 用户故事

1. 作为**视频团队负责人**，我希望一条 88 分钟的直播回放不再"一窗一窗地等"，以便当天就能看到候选、当天就能安排剪辑，而不是隔一天。
2. 作为**剪辑同事**，我希望二剪成片的每个接缝都没有"咔哒"声，以便交片前不必再手工补音频淡入淡出。
3. 作为**剪辑同事**，我希望长等待段被**快放**而不是被**跳掉**，以便保留现场连续性、看不出被剪过的痕迹。
4. 作为**剪辑同事**，我希望拿到的不只是一条 MP4，而是**能直接拖进 Premiere / 达芬奇的工程文件**，以便在你们挑好的片段上继续精修，而不是从头看 88 分钟挑素材。
5. 作为**对成本负责的人**，我希望提速不带来任何重复付费，以便预算不失控、账单可解释。
6. 作为**后续开发者**（P2），我希望剪辑决策是结构化数据而不是渲染代码里的字符串，以便以后加新能力时不用每次改渲染器。

## 3. 技术规范

### 3.1 需求池（P0 / P1 / P2）

> **分级原则**：P0 = 用户明确点名的（粗剪速度、精剪基础剪辑、复刻开源能力中最关键的部分）；P1 = 明显高价值且低风险；P2 = 架构性/可延后。

---

#### 【P0-1】粗剪 A · 腾讯 ASR 分片并发

- **需求描述**：`_transcribe_long_file`（`backlot/tencent_asr.py:518-...`）现在是 `for index in range(total)` 逐片「切音频 → 提交识别 → 落盘」串行。改为**有界并发**：分片相互独立（每片有独立 offset 与独立缓存 `chunk-{index:05d}.json`），可并发切分并并发提交；结果**按 offset 升序合并**，与串行版逐字一致。
- **验收要点（可离线测）**
  1. 分片数不变（88.9 分钟 = ⌈5333/600⌉ = 9 片），付费请求数不变；同一素材二次运行 `chunk-*.json` 全部命中、**0 次新提交**。
  2. 输出 `segments` / `text` / 时间轴与串行版**逐字节一致**（合并顺序不受并发影响）。
  3. 并发上限可配（默认 3，环境变量/常量），**上限 1 时等价于现状**（有自己的等价性用例）。
  4. 单片失败（超时/5 MB 超限/HTTP 非 2xx）→ **只重试该片**，已成功分片不重算；「**提交已受理但结果不明**」的片必须落盘 `reference` 并**停止自动重复提交**（沿用现有语义），给出中文补救说明。
  5. 假 runner / 假 requests 注入：断言**最多 N 片同时在飞**、总提交次数 = 分片数。
- **影响面**：`backlot/tencent_asr.py`（并发调度 + 合并）；`docs/handoff/` 一行说明。
- **风险**：**中**。① provider 限流（腾讯一句话识别/录音文件识别有 QPS 限制）→ 必须把并发上限压到 3 并实现**退避重试**，不能把 429 当致命错误；② 合并顺序错位 → 时间轴全错（用「按 offset 排序后再合并」+ 逐字比对用例挡住）；③ 分片边界本来就可能错一两个字（已知代价，本次不改切分策略）。

#### 【P0-2】粗剪 A · 视觉窗口并发

- **需求描述**：`backlot/material_interactions.py:553` 的逐窗口循环是**付费调用的串行点**（34 次视觉调用）。要求把它改成**有界并发调度**：窗口的**本地部分**（12 帧抽帧 + 联系表 `_contact_sheets`）与**付费视觉调用**进入同一并发池；**并发上限默认 1（等于现状）**，可显式开到 2–4；失败窗口**可单独重试**且**不改动已完成窗口的付费日志**。
- **必须保住的四条性质（这是本条的真正验收口径）**
  1. **不重复计费**：每个窗口的 `_remote(directory/f"{window['id']}-model.json", request_signature=...)` 幂等语义不变；命中即 0 付费；`ambiguous` 仍必须冻结人工核对（`confirm_ambiguous_not_accepted`）。
  2. **窗口数与调用数不变**：`usage.model_calls` 与串行版相同；边界复核（`boundaries-model.json`）仍**只调 1 次**。
  3. **结果可选地等价**：并发上限 = 1 时，产物与现状**逐字节一致**。
  4. **降级可见**：并发导致某窗口失败时，沿用现有的「整窗跳过 + `rejected_model_events` 留痕」路径，并在界面给出中文原因与「重试该窗口」提示，**不得**让整条素材作废。
- **验收要点**
  1. 假 `analyze` + 假 `_extract_frame`：断言「在飞窗口数 ≤ 上限」「窗口数不变」「调用数不变」「乱序返回也能正确 merge」。
  2. 真素材：S-001 端到端跑完，`usage.model_calls == 35`、事件数 28、**与串行版事件集合一致**（允许的时间戳级差异必须有界并如实记录）。
  3. 提速目标：**分析墙钟下降 ≥ 40%**（并发 4）；若因窗口间依赖只能做到 ≤ 20%，**必须如实记录并把实际值写进结论**（不得把目标改写成"已完成"）。
  4. `material-interaction-index.json` 的 `signature` 字段值与内容哈希**不变**。
- **影响面**：`backlot/material_interactions.py`（窗口调度、`usage` 统计、失败留痕）；`backlot/workbench.py`（进度文案：`正在分析互动窗口 x/y` 改成带并发的 `并发 4 路 · 已完成 x/y`）；`backlot/ui/workbench.js` 一行状态。
- **风险**：**高**（本次最大技术风险）。
  - **窗口间存在顺序依赖**：窗口 N 的付费 payload 里带 `previous_events`（`:563` `context = [x for x in events if x["end"] >= window["start"] - 6]`），并发会改变 payload → 改变 `request_signature` → **在途（未完成）的已付费窗口日志会作废**，被迫重新付费。→ 见 §3.3 待确认问题 1，**必须由架构师先定合同再动手**。
  - **已完成的索引不受影响**：命中即 `cache_hit` 提前返回（`:515-519`），34 个窗口不会重算；此点必须在验收里显式证明（索引哈希不变）。
  - 并发下的内存/句柄峰值（34 窗口 × 联系表 + 帧），必须限制在飞窗口数。

#### 【P0-3】精剪 B · 切口音频淡化（消爆音）

- **需求描述**：`_filters`（`material_interaction_second_pass_render.py:167-208`）现在每段的音频链只有 `atrim → asetpts → aresample/aformat → atempo`，拼接后 0.32s 级的多段切割累积问题虽已用 `tpad` 修好画面，但**音频在每个接缝仍是硬切**。要求：**每段音频在进入 `concat` 前加 5–15ms 的淡入淡出**（`afade=t=in` + `afade=t=out`，默认 **8ms**，可配 5–15ms），使 26 个硬切点 → 0。整个成片**首尾各加 150–300ms 淡入淡出**（P1-3，可一并做，共用同一机制）。
- **验收要点**
  1. 单测：滤镜串里每个音频段都含一对 `afade`；`afade` 的 `st` 依据该段**变速后**的输出时长计算（`(end-start)/speed`），**不是源时长**；淡出不得把 `atrim=duration=` 的总时长改掉（`afade` 不改变时长，需断言输出时长与改动前一致到 1ms）。
  2. 单测：`afade` 时长参数越界（<5ms / >15ms）→ 可读中文错误。
  3. 单测：**关掉开关时滤镜串与现状逐字一致**（等价性保护）。
  4. 真素材：S-001 的 R0007（13 处切口）重渲染，`ffprobe` 输出时长不变、QA 仍 `passed`；用一段**独立脚本**（不经被测代码）在 26 个接缝处检测**样本级不连续**（相邻样本绝对差超过阈值的次数），证明接缝能量跳变显著下降；人工听辨结论写入结论。
  5. **零新增付费调用**、`VERSION` 必须升位（渲染签名含版本，否则旧预览会被误判缓存命中）。
- **影响面**：`backlot/material_interaction_second_pass_render.py`（`_filters` + 选项透传 + `VERSION`）；`backlot/material_interaction_second_pass.py`（`normalize_options` 新增 `audio_fade_ms`、`edge_fade`）；`backlot/ui/workbench.js`（开关）。
- **风险**：**低**。纯 FFmpeg 滤镜；主要坑是 `afade` 时间基准（必须在变速后算）与「淡出吃掉了最后一帧音频」——用时长断言挡住。

#### 【P0-4】精剪 B · 「等待段加速」原语（复刻 auto-editor 的 `speed:1.5`）

- **需求描述**：现在等待段只有两个结局——**整段删掉**（产生跳切）或**原样保留**（拖沓）。新增选项 `pause_handling ∈ {remove, speed_up, off}`：
  - `remove` = 现状（删掉中段、两端各留呼吸），**默认值，保持已验收行为不变**；
  - `speed_up` = **不删**，把等待段按 `pause_speed`（默认 2.0，范围 1.5–4.0）**快放**，效果等同 auto-editor 的 `--when:N speed:1.5`；
  - `off` = 不处理。
- **验收要点**
  1. 计划层：`speed_up` 模式下，等待段仍是 `occurrences` 的一段，但 `speed = pause_speed`，且**不产生 `pause_trims`**；`_rebuild` 校验能接受 `speed` 段（现有校验只认 1.0/1.1/1.25 的整体倍速，须新增「段级倍速」概念并写清优先级）。
  2. 渲染层：`atempo` **单实例上限为 2.0**，`pause_speed > 2.0` 必须**链式**（如 4.0 → `atempo=2,atempo=2`）；单测断言 4.0 时链路正确且总倍率为 4.0±1e-6。
     - **实现偏差（已裁决）**：实现为单实例 `atempo`，偏离原链式要求；理由：项目固定的 static-ffmpeg 8.0.1 实测支持 [0.5,100]，`pause_speed` 上限 4.0，链式属无谓复杂度。验收判据以「单实例且乘积精确、越界抛中文可执行错误」为准。
  3. 时长可预测：输出时长 = Σ `(end-start)/speed`，与 `timeline_mapping` 一致（误差 < 1ms）；字幕 `output_start/end` 提升到**输出时间轴**且单调，仍落在 `[0, output_duration]`。
  4. 真素材：在 R0007（父候选 143.6s）上各跑一次 `remove` 与 `speed_up`，出片均 ≤ 60s、QA `passed`；`speed_up` 版**源片重复 = 0、无删剪跳切**；把两条产物的帧间差异与人工观感结论写入结论。
  5. 与「压缩对话间停顿」的关系必须在界面上说清、在计划里互斥（不能同时删和快放同一段）。
- **影响面**：`backlot/material_interaction_second_pass.py`（选项、`occurrences` 段级倍速、校验）、`material_interaction_second_pass_render.py`（`atempo` 链式）、`material_interaction_second_pass_candidates.py`（透传）、`workbench.js`（开关 + 倍速下拉）。
- **风险**：**中**。① 改的是**渲染语义**，历史计划必须仍可读（`SUPPORTED_VERSIONS` 保留 v1/v2/v3）；② 变速段的**音画同步**：视频 `setpts/PTS` 与音频 `atempo` 必须同倍率，否则掉帧（V3 的 `tpad` 修复只覆盖画面落后，不覆盖倍率不一致）——用「每段输出时长 == `(end-start)/speed`」的双向断言挡住；③ 快放后听感可能"花哨"，**默认关闭**，由用户勾选。

#### 【P0-5】导出 C · 通用 JSON 剪辑清单 + Premiere/FCP7 XML

- **需求描述**：新增导出能力（当前 `backlot/workbench.py` **零 export 接口**）。从**已冻结的二次精剪计划**（`plan` + `timeline_mapping` + `subtitle_cues` + `pause_trims`）生成两种文件：
  - **① 通用 JSON 剪辑清单**（自有 schema，`cut-list-v1`）：媒体路径与指纹、`contract`（fps/宽高）、`segments:[{segment_id, source_start, source_end, speed, output_start, output_end, role}]`、`subtitles:[{output_start, output_end, text}]`、`pause_handling`、`degradations`、生成时间与来源 `plan_id/revision`。
  - **② FCP7 XML（`xmeml` v4）**：Premiere Pro / DaVinci Resolve / FCP 均可导入。**必须把倍速段拆成"变速片段"或退化为"等长片段 + 标记"**（XML 对变速表达有限，须写清退化策略），字幕写成**时间线标记（marker）**并把 SRT 作为旁挂文件一起导出。
  - 落盘位置：`projects/<项目>/artifacts/media-index/<资产>/interaction-second-pass/<plan_id>/export/<plan_id>.{json,xml}`，与预览同目录、**不覆盖任何既有产物**。
- **验收要点**
  1. 单测：JSON 能被自己的解析器读回，`segments` 覆盖 `timeline_mapping` 全部条目，`Σ(output_end-output_start) == output_duration`（±1ms）。
  2. 单测：XML 是**合法 XML**（能被 `xml.etree` 解析），`<sequence><rate><timebase>` 与 `contract.fps` 一致，片段入出点用**帧号**而非秒（按 fps 换算，含四舍五入规则），**不允许出现负值或超出素材时长的帧号**。
  3. **端到端（人工）**：在 Premiere 或达芬奇里**成功导入 ≥1 个文件**，画面段序、总时长、字幕位置与预览一致；把导入截图/结论写入结论。
  4. **导出不覆盖（去「幂等」措辞）**：同一 `plan_id` + `revision` 重复导出**每次生成新文件（按内容哈希命名），不会覆盖既有产物**；除 `generated_at` 生成时间字段外，两份内容一致。默认路径不固定生成时间，故**不宣称字节幂等**（PRD 原表述「逐字节一致」已按此更正）。
  5. **零副作用**：导出**不触发任何付费调用**；不改动 `plan` 文件（导出前后哈希不变）；`plan.preview.stale` 语义不受影响。
  6. 未 `确认入库` 的计划**也能导出**（导出是"给人看的起点"，不应被入库流程卡住），但界面必须标注「此计划尚未确认入库」。
- **影响面**：**新增** `backlot/material_interaction_export.py`；`backlot/workbench.py`（新增导出入口 + 一段 HTTP 接口）；`backlot/ui/workbench.js`（导出按钮 + 格式选择 + 结果提示）；`tests/backlot/test_material_interaction_export.py`（新增）。
- **风险**：**中**。① **对外新契约**（一旦有同事在用，格式就不能随便改）→ 必须带 `version` 字段；② FCP7 XML 对**变速**和 **HEVC/TS 源**支持参差 → 见 §3.3 待确认问题 5（媒体引用用原片还是审核代理）；③ 帧号舍入累积误差 → 用「段边界帧号单调不减 + 总帧数与输出时长相符」断言。
