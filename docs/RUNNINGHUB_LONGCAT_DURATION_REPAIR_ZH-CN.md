# RunningHub LongCat 时长修复说明

## 结论

原工作流存在三项相互叠加的时长缺陷：毫秒被当成秒、续段次数没有扣除重叠帧、最终输出没有按音频裁切。2 秒音频因此可能被规划为约 33 分钟视频，并在真实语音结束后继续生成无效口型动作。

修复后的正式工作流：

`D:\codex_work\OpenMontage\config\runninghub\longcat_avatar_api.json`

原始下载文件保持不变，作为故障样本和来源记录：

`C:\Users\61442\Downloads\LongCat-1.5_檬檬雅雅_全自动时长_320x576_中文标注版_api.json`

## 修复内容

| 节点 | 修复前 | 修复后 |
|---|---|---|
| `529` 音频秒数 | `a` | `a / 1000.0` |
| `546` 续段次数 | `ceil(a/b)-1` | `max(0, ceil((a-b)/(b-c)))`，其中 `c` 连接节点 `148` 的 13 帧重叠量 |
| `292` 首段预览 | `trim_to_audio=false` | `trim_to_audio=true` |
| `352` 最终 MP4 | `trim_to_audio=false` | `trim_to_audio=true` |

工作流仍以 101 帧作为 LongCat 单次最小生成块。对于 2 秒音频，模型内部仍生成约 4.04 秒画面，但最终 MP4 会通过原始音频严格裁切到约 2 秒；多生成的尾部不会进入成品。

## 防回归机制

1. `load_longcat_workflow_template()` 会在任何付费任务前检查单位换算、节点连线、续段公式和音频裁切开关。
2. `scripts/import_runninghub_workflow.py` 导入旧版 JSON 时会自动修复，不再原样复制缺陷。
3. API 的 `nodeInfoList` 每次提交都会再次覆盖节点 `529`、`546`、`292`、`352`，即使远端仍是旧版已发布工作流，也不会再使用危险公式。
4. 自动测试覆盖 2、5、12、20 秒输入，并验证长音频续段生成帧数不会少于目标帧数。

## RunningHub 手工部署

如果继续在 RunningHub 网页中手动测试，需要把修复后的正式 JSON 重新导入工作台并保存。网页手动运行不会经过 OpenMontage 的 API 安全覆盖，因此不能继续使用旧工作流。

建议按以下顺序验证：

1. 导入修复版 JSON，确认节点 `529` 显示 `a / 1000.0`。
2. 确认节点 `546` 已连接第三个输入 `c`，公式为重叠感知版本。
3. 确认最终节点 `352` 的 `trim_to_audio` 已开启。
4. 使用 2 秒音频试跑，输出应接近 2 秒，不应继续生成几十分钟。
5. 再使用 5 秒和 12 秒音频检查续段边界、嘴型以及输出时长。
6. 验收后发布工作流，把网址末尾的 `workflowId` 保存到 OpenMontage 工作台。
